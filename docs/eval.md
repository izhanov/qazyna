# Eval качества поиска qazyna

Как измерять качество поиска, чтобы любая правка ранжирования была «до/после»
по цифрам, а не «вроде стало лучше».

English version: [eval.en.md](eval.en.md).

## Золотой набор

Файл на 15–20 кейсов «запрос → ожидаемый файл». Лежит там, где удобно
пользователю — команда принимает путь; в этом репо стартовый набор
живёт в `evals/golden.yaml`:

```yaml
- query: "что мы должны сделать чтобы подготовить тикет для деплоя?"
  expect: ["kit-help/resources/help-text.md"]
- query: "как задеплоить на препрод"
  expect: ["skills/deploy/SKILL.md", "infra-deploy-preprod/SKILL.md"]
```

Правила:

- Ожидание — на уровне **файла** (матч по суффиксу пути), не чанка:
  ординалы чанков плывут при смене нарезки, «нашли нужный файл» — стабильный
  критерий.
- Кейсы брать из реальных запросов (история CLI). Каждый раз, когда поиск
  в быту сработал плохо, запрос отправляется в golden.yaml — набор
  превращается в регрессионный.

## Метрики

- **recall@5** — доля кейсов, где ожидаемый файл попал в топ-5.
  Главная цифра «поиск находит».
- **MRR** (mean reciprocal rank) — среднее 1/позиция первого правильного
  результата. Чувствительна к порядку: сдвиг ответа с 5-го места на 1-е
  recall не меняет, а MRR растёт с 0.2 до 1.0. Именно она покажет эффект
  декомпозиции запроса и реранкера.

## Харнесс: `qazyna eval <golden.yaml>`

Сабкоманда, не Go-тест: нужны живой индекс и Ollama, с фейковым эмбеддером
семантику не измерить. Команда обходит кейсы, зовёт тот же `search.Search`,
печатает строку на кейс (позиция найденного файла или «miss») и агрегат.

Флаг `--mode` — прогнать vector/text/hybrid раздельно, чтобы увидеть, даёт ли
гибрид что-то сверх чистого вектора на русских запросах по английским докам
(лексическая половина там почти не матчит).

## Дисциплина сравнения

- Между «до» и «после» индекс не трогать — иначе меришь не правку, а новый
  корпус.
- Исключение — правки чанкинга: там переиндексация и есть изменение.
  A/B через два разных `--db` пути.
- Смотреть не только агрегат, а diff по кейсам: +2 кейса и −2 кейса дают
  тот же recall, но это регрессия, которую агрегат прячет.

## Контекст: очередь улучшений поиска

Эвал — первый шаг. Дальше по убыванию эффекта:

1. Декомпозиция конверсационного запроса на предложения + слияние
   существующим RRF.
2. Пул кандидатов для RRF: сейчас `limit*3` = 15, поднять до 30–50.
3. Дедуп по файлу: не больше 2 чанков одного файла в выдаче.
4. Чанкинг: склейка секций короче ~200 символов (убирает мусорные
   мини-чанки), оверлап 1–2 предложения, жёсткий сплит по границе
   предложения. Любая правка нарезки требует полной переиндексации.
5. Реранкер (bge-reranker-v2-m3) — самый большой прирост, но у Ollama нет
   rerank API: конфликт с принципом «Ollama only».

Примечание про скоринг гибрида: плоские скоры ~0.5 в кросс-языковых
запросах — не слабость модели, а потолок RRF-нормировки (1.0 = первый
в обоих списках, 0.5 = первый только в одном; лексический список на
русском запросе по английским докам пуст).
